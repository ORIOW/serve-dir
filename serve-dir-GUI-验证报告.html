serve-dir GUI 工具：验证不通过

对 dsh 按「把 serve-dir 技能做成带 UI、无终端窗口的可运行小工具，支持文件多选下载与四项自定义」这一任务交付物（scripts/serve_dir_gui.py、SKILL.md）的独立验证结论与全部证据。

验证日期2026-10-29
验证对象serve_dir_gui.py · SKILL.md · serve_dir.py（基座）
运行环境Windows · Python 3.12.10（Tk 8.6）
方法静态审读 + 命令行/无头/进程级实测 + 独立复审
结论 · 不可交付

7 项要求中 3 项满足、1 项部分满足、3 项未满足；另存在 2 个使主流程完全不可用的致命缺陷。工具当前不存在任何一条「能启动并维持服务」的完整路径：文档推荐的启动命令触发无限进程重生链、窗口永不出现；唯一能打开窗口的 pythonw 路径上，「启动服务器」按钮又必然被错误的自检逻辑判为失败并自动停服。

本次验证中最重的一项代价：为肃清文档式启动残留的隐形进程链，先后执行 950+ 次 taskkill /T /F、跨约 80 分钟仍无法根除，最终靠 12 秒断粮战术（瞬时隔离脚本文件）才肃清——该缺陷的实战危害以此为准。

02

致命缺陷一：文档式启动触发无限进程重生链

serve_dir_gui.py 的 main()（283–297 行）意图是「检测到用 python.exe 启动就转交 pythonw.exe 以隐藏控制台」，但实际代码用 sys.executable——即仍然是 python.exe——重新拉起自己：

def main():
    # Windows 下用 pythonw.exe 运行可隐藏控制台窗口
    if sys.platform == "win32":
        if not sys.executable.lower().endswith("pythonw.exe"):
            subprocess.Popen(
                [sys.executable, "-u", __file__],   # ← 仍是 python.exe，不是 pythonw.exe
                creationflags=subprocess.CREATE_NO_WINDOW,
            )
            return                                   # ← 永远到不了 tk.Tk()
    root = tk.Tk()
    ...

每个子进程与其父代完全相同（python.exe），再次命中同一分支、再拉起下一代后立刻退出——形成一条无限接力链，链上没有任何一代能到达 tk.Tk()。注释声称「由 pythonw.exe 隐藏控制台」，代码却从未引用 pythonw.exe。

实测结果（三项独立实验）

  • 文档命令启动（python serve_dir_gui.py）：启动器约 1 秒退出、无任何窗口；随后 60 秒持续采样观测到 33 个不同 PID 的接力进程，每约 2 秒一代，从不自行终止（附录 B.4）。
  • 单代复现（在已验证清零的环境中，按代码内部完全一致的形态启动一代）：16 秒内再产生 4 个新代；该链条此后至少存活 6 分钟仍在生成新代。全程 stderr 为 0 字节——各代都是正常退出，重生是设计使然，不是崩溃。
  • pythonw 对照（唯一可行路径）：单进程稳定挂驻 60 秒，窗口真实出现（标题 serve-dir — 局域网文件服务器，MainWindowHandle 非零），未点按钮时零监听端口（附录 B.3）——证明只有 pythonw 分支能到达 mainloop。

影响

用户按 SKILL.md 推荐命令（python skills/serve-dir/scripts/serve_dir_gui.py）启动：控制台一闪即退，永远没有界面；同时一条隐形进程链常驻后台空转。肃清实测：先后累计 950+ 次 taskkill /T /F、约 80 分钟仍无法根除——每代 spawn 完下一代后数毫秒内自行退出，轮询式击杀几乎永远打在已退出的代际上（实测：查询列出的进程在下一次调用时已 not found）；期间还发现 WMI 会偶发把这些短命进程的命令行读成空串，导致按命令行过滤的常规杀法完全失明（附录 B.4）。最终靠 12 秒断粮战术（瞬时隔离脚本文件，使所有新 spawn 因「can't open file」瞬间失败）才根除——普通用户几乎不可能自己停掉它。

03

致命缺陷二：启动自检必然误判，GUI 的核心按钮不可用

即使用户有幸用 pythonw 打开窗口，「启动服务器」流程末端的自检（_verify_server，GUI:250–277）把「根目录自身的名字」当作特征串去列表页 HTML 里找：

content = response.read().decode("utf-8", errors="ignore")
if os.path.basename(root) not in content:
    self.stop_server()
    messagebox.showerror("错误", f"启动失败：返回的内容不包含目录 '{...}'...")

但根目录的列表页只包含子项的名字和固定标题（📁 文件列表），永远不包含根目录自己的名字。因此该断言对绝大多数目录恒为假：服务器明明已经成功启动，GUI 却立即弹「启动失败」并自动把它停掉。

实测结果

  • 无头复刻同一断言：服务目录 sd_verify_gui（内含 one.txt / two.txt），列表页正常返回 200 且正确列出文件，但断言 basename in content 结果为 False（B.2-B1）——即 GUI 必然误报启动失败并停服。
  • 连带效应：端口被占用时，ThreadingHTTPServer 的 allow_reuse_address=True 在 Windows 上会静默双绑定（实测：新 server 无报错绑定成功、UI 显示「运行中」，但 GET 超时——连接仍被先绑定的旧监听者吞掉，B.2-E）。此时自检反而「碰巧」报错，错误信息却指向错误的原因。

结论：GUI 不存在任何一条「启动 → 维持服务」的成功路径。

04

功能性缺失：多选/下载为零，写开关是摆设

4.1 文件多选 + 下载按钮（要求 3、4）

GUI 全文没有任何文件列表、复选框或下载相关代码；网页端 PRETTY_HTML（serve_dir.py:28–45、85–90）每行只有一个 <a> 链接。无头实测抓取页面检查：page contains checkbox/download UI → False。要求未实现。

4.2 「允许 client 写入」开关（要求 7）

复选框存在且默认只读（方向正确），但 allow_write_var 在两份文件中除 UI 绑定外零消费；服务端仅 SimpleHTTPRequestHandler 的 GET/HEAD，实测 PUT 与 POST 均返回 501、磁盘无新文件（B.1、B.2）。控件标签自己写着「需修改 serve_dir.py」——这是把「未实现」直接发布给了最终用户。

SKILL.md 的声明与实际说明
「GUI 启动（推荐）：python …/serve_dir_gui.py」不符这正是触发无限重生链的命令；窗口永不出现。能用的只有正文一句带过的 pythonw 直启

GUI 配置说明（目录/端口/pretty）不完整未列「允许写入」复选框（因其未实现），更未提多选/下载（完全缺失）
07

修复建议（交 dsh 执行）

按优先级排列；每条附验收标准。P0 全部完成前不应再次交付。

P0消除无限重生链：真正切换到 pythonw，或直接交付 .pyw

判定分支内显式使用 os.path.join(os.path.dirname(sys.executable), "pythonw.exe") 拉起（并检查存在性），加环境变量哨兵防递归；或更简单——交付 serve_dir_gui.pyw（双击即无控制台），删除 main() 里的自我重启逻辑。

验收：以 PATH 上的 python.exe 执行脚本后，30 秒内进程数恒为 1、出现标题为「serve-dir — 局域网文件服务器」的窗口；60 秒采样无第二个 PID。

P0重写启动自检：断言必须指向「确实在服务所选目录」

改为：等待 bind（带 3 次 × 0.3s 重试）→ HTTP 200 → 校验页面包含 os.listdir(root) 的首个子项名（而非根目录自身名）；或校验响应条目数与 len(listdir) 一致。绑定失败要在线程外同步感知（先 bind 再交给线程 serve_forever），把真实错误弹给用户。

验收：对不含同名子项的目录点「启动服务器」，状态保持「运行中」且 curl 可取到正确列表；对被占用端口点启动，弹出真实原因并回到「未启动」。

P0写开关：要么实现，要么移除——不许保留欺骗性 UI

若实现：PUT/POST 处理器 + serve_root 路径逃逸防护（commonpath 校验）+ 大小上限；若不实现：删复选框，SKILL.md 同步标注「只读」。

验收：勾选后 PUT 落盘且路径逃逸被 403 拒绝；未勾选时 PUT 返回 403/501。

P1文件多选 + 下载按钮

建议做在网页端（client 才需要下载）：列表页加复选框 + 「下载所选」，服务端新增 GET /__download?names=… 流式打 zip（同样要路径逃逸防护）。GUI 内多选对服务器场景意义有限，如用户本意是 GUI 侧，请先与其确认。

验收：浏览器勾选多个文件（含中文名/空格）打包下载成功，zip 内路径不越界。

P1端口占用防线 + 打开浏览器 + 输入校验

绑定前探测目标端口并提示（或 allow_reuse_address=False + 捕获 WinError 10048 给出明确弹窗）；open_browser 改 webbrowser.open（消除黑窗与双标签）；端口输入 try/except TclError 给行内提示。

验收：预占端口后再点启动，得到「端口被占用」弹窗而非假「运行中」；pythonw 下点「打开浏览器」无黑窗。

P2卫生项

os.chdir 改为在 Handler 内用绝对根映射路径；删除死导入与重复类；stop 中补 server_close() + join；目录框回车改为「应用输入」而非弹浏览框；SKILL.md 同步真实行为并明确「pythonw 是唯一启动路径」；__pycache__ 移出技能目录。

  • 未覆盖项：真实点击 GUI 按钮（Tk 自动化未做，相关逻辑以无头复刻代替）；多实例并发；审阅者提出的「黑窗」「竞态」等静态推断未逐一实测，均已在正文标注「静态推断」。
